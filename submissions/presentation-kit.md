## ❓ Q&A — คำถามกรรมการที่น่าจะถาม + คำตอบ

**Q: ต่างจาก RAG / chatbot ทั่วไปยังไง?**
A: RAG คือ "หา→ตอบ" เรา**ตัดสินก่อนว่าควรใช้ AI ไหม** — งานที่ตัดด้วยกฎได้ตอบเองเลย 0 token
และ kernel **เรียนรู้** ว่างานแบบไหนไม่ต้องเปลืองเงิน AI RAG ไม่มีชั้นตัดสินใจนี้

**Q: "ลด 80%" มาจากไหน พิสูจน์ได้ไหม?**
A: จากสัดส่วนงานที่เข้า FastPath (ตัดสินด้วยกฎ) — ดูสดได้ที่ dashboard ซึ่งนับจาก traffic จริง
ยิ่งงานหน่วยงานเป็น routine มาก สัดส่วนยิ่งสูง และ kernel เรียนรู้ให้สูงขึ้นอีกจาก feedback

**Q: kernel ตัดสินผิดล่ะ? เช่นคัดงานยากเป็น FastPath?**
A: 3 ชั้นกัน — (1) seeded weights ตั้ง bias ให้งานคลุมเครือ escalate, (2) feedback loop ให้คน
แก้ให้ kernel เรียนรู้, (3) ทุก decision มี proof ตรวจย้อนได้ว่าตัดสินด้วยอะไร ถ้าผิดก็ revert policy ได้

**Q: ทำไม BLAKE3 ไม่ใช่ hash อื่น?**
A: เร็ว, reproducible, และเป็น proof ที่รันซ้ำได้ผลเดิม — เหมาะกับ audit ที่ต้องพิสูจน์ได้ว่า
"input เดิม → decision เดิม" ซึ่งเป็นหัวใจของ accountability

**Q: ข้อมูลนักศึกษาส่วนตัวล่ะ ปลอดภัยไหม?**
A: แยกชั้นชัด — public knowledge ตอบในเบราว์เซอร์ (ไม่มี PII) ส่วน personal data ต้อง login
(SSO มหาวิทยาลัย) → API ที่ auth แล้ว → database แยก row-level ตาม PDPA. วันนี้โชว์ Tier 1
(public) ที่ใช้ได้จริงแล้ว

**Q: scale ได้ไหม ต้นทุนเท่าไหร่?**
A: รันบน Cloudflare edge — Workers 100k req/วัน + D1 5GB + Pages ฟรี ครอบคลุม demo ถึงใช้จริง
ระดับหน่วยงาน $0 และ fast path ไม่เสีย token เลย ยิ่ง scale ยิ่งคุ้ม

**Q: ใช้กับระบบที่หน่วยงานมีอยู่แล้วได้ไหม?**
A: ได้เลย — เราเป็น "ชั้นคัดกรอง" เสียบหน้า LINE/เว็บ/API ที่มีอยู่ มี LINE adapter เป็น
Worker แล้ว (เรียก kernel ผ่าน service binding) เปลี่ยน KB และ LLM เป็นของหน่วยงานได้

**Q: Kiro / Amazon Bedrock อยู่ตรงไหน?**
A: LLM path ออกแบบให้ต่อ Bedrock/Gemini ได้ (demo ใช้ Gemini) และ Kiro Hook เป็นทางเข้า
งานอัตโนมัติ — kernel คัดก่อนเสมอ เรียก LLM เฉพาะที่จำเป็น

**Q: ถ้า AI ล่ม/throttle ล่ะ?**
A: fast path ไม่พึ่ง AI เลย → ยังทำงาน 80% ของงานได้ปกติ นี่คือข้อดีของการมีชั้นคัดกรอง —
ระบบไม่ล่มทั้งหมดเมื่อ LLM มีปัญหา
