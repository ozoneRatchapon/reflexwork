# Q&A Bank — ธนาคารคำถาม-คำตอบกรรมการ (5 นาที)

> ช่วงตอบคำถาม 5 นาที = **10 คะแนน + กู้คะแนนเกณฑ์อื่นได้**. กรรมการ 7 ท่าน
> (ผู้บริหาร + วิชาการ + อุตสาหกรรม) → เตรียมคำถามทั้ง 3 มุม.
> **หลักตอบ:** ตรง + สั้น (30-45 วิ/ข้อ) + ซื่อสัตย์. ไม่รู้ = "ยังไม่ได้ทำ แต่ออกแบบไว้ว่า..."
> อย่าเถียงกรรมการ — รับแล้วต่อยอด.

## กลุ่ม A — ผู้บริหาร / Impact / Business

### Q1. "ต่างจากการเอา ChatGPT มาตอบตรง ๆ ยังไง?"
ReflexWork **ไม่ได้แข่งกับ ChatGPT** — มันวาง *หน้า* AI ตัวไหนก็ได้. ต่างตรง:
AI ตอบทุกคำถาม = แพง + มั่วตัวเลขได้ + ตรวจย้อนหลังไม่ได้. เราคัดคำถามซ้ำ ~80%
ออกก่อน ตอบเองฟรี เหลือเฉพาะที่ยากจริงส่งให้ AI — **ถูกลง เร็วขึ้น และทุกคำตอบ
มีหลักฐาน** ที่ ChatGPT เปล่า ๆ ให้ไม่ได้.

### Q2. "ลด 80% จริงไหม วัดจากไหน?" ★ ต้องซื่อสัตย์
ตัวเลข 80% เป็น **design projection จากสัดส่วนคำถามซ้ำ/FAQ** ที่เราสังเกตจากเคสจริง
— **ยังไม่ได้วัดจาก production load เต็ม**. บน demo ตอนนี้ fast-path จริงอยู่ที่ ~87%
ของ 31 คำถามที่รันผ่าน (เห็นใน `/status`). เราจงใจติดป้าย "ประมาณการ" ในเด็คเพราะ
ไม่อยากเคลมเกินจริง — ตัวเลขจริงขึ้นกับคุณภาพคู่มือของแต่ละหน่วยงาน.

### Q3. "ประหยัดเงินได้เท่าไหร่เป็นตัวเลข?"
ขึ้นกับปริมาณคำถาม + ราคา token ของ LLM ที่ใช้. หลักคือ: ทุกคำถามที่ FastPath จับได้
= **0 token = 0 บาท**. ถ้าคำถามซ้ำ 80% จริง ต้นทุน LLM ลดตามสัดส่วนนั้น. เราวัดจริง
ได้เมื่อ deploy กับหน่วยงานจริง — ตอนนี้ให้เป็นกรอบการคำนวณ ไม่ใช่ตัวเลขมั่ว ๆ.

### Q3b. "มีหลักฐานไหมว่าปัญหา token แพงนี้มีจริง ไม่ใช่คิดเอง?" ★ proof จากสนามจริง
มีครับ — **ทีมผู้ช่วย AI อีกทีมในมหิดลเอง** (แนว LLM-first ยิงทุกคำถามเข้าโมเดล)
รายงานเองช่วงทดสอบว่า **"token พุ่งก้าวกระโดด"** และ dashboard สรุปค่าใช้จ่ายได้
ไม่แม่น (เคยโชว์ $0.00 ทั้งที่ไม่ได้ฟรี เพราะจับคู่ราคาโมเดลไม่ได้). นี่คือเหตุผลตรง ๆ
ที่ ReflexWork เกิดมา: **คำถามซ้ำที่ FastPath จับได้ = 0 token = นับได้ว่าประหยัดเท่าไร**
ต่างจาก LLM-first ที่แม้แต่ทีมเก่ง ๆ ยังวัด cost ให้แม่นได้ยาก.
> ⚠️ พูดเป็น "ปากคำทีมจริงในมหิดล" ไม่ใช่ metric เรา — ไม่เอ่ยชื่อทีม/repo เว้นแต่ได้อนุญาต.

### Q4. "หน่วยงานไหนได้ประโยชน์ นอกจากบัณฑิตวิทยาลัย?"
ทุกหน่วยที่มี FAQ ซ้ำ ๆ: ทะเบียน, การเงิน, IT help desk, หอพัก, วิเทศสัมพันธ์.
เราออกแบบเป็น **federated corpus** (spec `distributable-kernel`) ให้แต่ละหน่วย
ติดตั้งของตัวเอง ใช้คู่มือตัวเอง แต่เรียนรู้ร่วมกัน — ดู Q11.

## กลุ่ม B — วิชาการ / เทคนิค

### Q5. "ตัวคัดกรองเป็น AI หรือ if-else?" ★ ตอบตรงไปตรงมา
**แยกให้ชัด:** ส่วนที่เป็น **กฎ** (regex) คือตัวจับ smalltalk/ประชด — จงใจเป็น
deterministic เพื่อ 0-token + ตรวจสอบได้. ส่วนที่ **ไม่ใช่ if-else** คือ sigmoid gate
(θ=0.72) ที่ตัดสิน route + การค้นคู่มือด้วย **TF-IDF cosine** (recall@1 82%).
เราเลือกกฎในจุดที่ต้องการความแน่นอน (fail-safe ไปทาง "ถือเป็นคำถามจริง") ไม่ใช่
เพราะทำ ML ไม่เป็น — มันคือ design decision เพื่อ auditability.

### Q6. "BLAKE3 proof มีไว้ทำไม ใครจะตรวจ?"
ทุกคำตอบผนึกเป็น hash จาก (คำถาม + เส้นทางที่เลือก). **รันคำถามเดิม → ได้ hash เดิมเป๊ะ**
= พิสูจน์ว่าระบบตัดสินแบบ deterministic ไม่ได้สุ่ม/มั่ว. ผู้ตรวจสอบ (internal audit,
PDPA officer) ใช้ยืนยันว่า "คำตอบนี้มาจากคู่มือหัวข้อนี้จริง ไม่ใช่ AI แต่งขึ้น".

### Q7. "AI ที่ใช้คือตัวไหน hallucinate ไหม?" ★
เราใช้ได้หลาย provider (Gemini / local Typhoon 3b / Bedrock). **กันมั่วด้วย 2 ชั้น:**
(1) ตัวเลข/เบอร์/วันที่ **มาจากคู่มือเสมอ** AI ไม่เคยเป็นแหล่งข้อเท็จจริง;
(2) เวลาเรียก AI เราบังคับ system prompt "ห้ามแต่งนอกคู่มือ" (grounded).
เราเคยเจอ Typhoon มั่วเบอร์ IT ปลอม → นั่นแหละเหตุผลที่ factual ต้องมาจาก KB เท่านั้น.

### Q8. "ข้อมูลนักศึกษาปลอดภัยแค่ไหน (PDPA)?"
ตัวคัดกรองเป็น WebAssembly รันในเบราว์เซอร์ 100% — **คำถามไม่ออกนอกเครื่อง**.
log ปิดบัง PII (เก็บแค่ topic + count ไม่เก็บข้อความดิบ). local AI ก็รันบนเครื่อง
มหาวิทยาลัยได้ (ข้อมูลไม่ไป cloud). federated corpus ส่งแค่สัญญาณที่ mask แล้ว
ไม่เคยส่งข้อความผู้ใช้.

## กลุ่ม C — อุตสาหกรรม / Readiness / Scale

### Q9. "พร้อมใช้งานจริงแค่ไหน หรือยังเป็น prototype?"
Live บน production **วันนี้** ที่ reflexwork.pages.dev (สแกน QR ลองได้). มี
production-hardening แล้ว: staff auth, D1 backup, tunnel token. **ที่ยังขาด** (ซื่อสัตย์):
load test ภายใต้ concurrency สูง + เติมคู่มือให้ครอบคลุมจากข้อมูลจริง + PDPA review
ของ retention window — ประเมินทำเสร็จได้ใน 1-2 เดือนถ้าได้ deploy กับหน่วยงานจริง.

### Q10. "Scale ได้ไหมถ้าคนใช้พร้อมกันเยอะ ๆ?"
ได้ดีเพราะ **FastPath รันในเบราว์เซอร์ผู้ใช้เอง** — ไม่กินทรัพยากร server เลย
(ต่างจาก chatbot ที่ยิง LLM ทุกครั้ง). server โดนเฉพาะ ~20% ที่ escalate.
edge (Cloudflare Workers) scale แนวนอนอยู่แล้ว. คอขวดจริงคือ LLM path ซึ่งเล็กลง
เพราะเราคัดออกไปแล้ว 80%.

### Q11. "ขยายไปทั้งมหาวิทยาลัยยังไง?" ★ จุดขาย scale
ออกแบบไว้เป็น **federated corpus** (spec `.kiro/specs/distributable-kernel/` ครบแล้ว):
แต่ละคณะ `install` ตัวคัดกรอง + คู่มือตัวเอง (private by default). ถ้า opt-in จะส่ง
**เฉพาะสัญญาณที่ปิดบัง PII** (topic + count) เข้า central. central รวมคำถามที่หลายคณะ
ตอบไม่ได้ → ร่างคำตอบ (คนอนุมัติ) → ปล่อยเป็นคู่มือกลางที่ลงนามดิจิทัล ให้ทุกคณะดึงไปใช้.
**คณะ A เติมแล้ว คณะ B ได้ด้วย โดยข้อมูลผู้ใช้ไม่ไหลข้าม.**

### Q12. "โมเดลธุรกิจ / ต้นทุนดูแลระยะยาว?"
ต้นทุนต่ำโดยดีไซน์: FastPath ฟรี (เบราว์เซอร์), edge worker ราคาถูก, LLM เรียกน้อยลง 80%.
ดูแล = เติมคู่มือ (ไม่ retrain model = ไม่มีต้นทุน GPU). ถ้าใช้ local Typhoon =
0 ค่า API. เหมาะเป็น **service กลางของมหาวิทยาลัย** ที่ทุกหน่วยเรียกใช้ซ้ำได้.

## คำถามดัก (เตรียมไว้ กันโดนจับ)

### Q13. "เห็นมี Solana/blockchain ในรีโป เกี่ยวอะไร?"
เป็น **future work บรรทัดเดียว** (on-chain settlement สำหรับ workflow ข้ามองค์กร) —
**ไม่ใช่ส่วนหลักของ ReflexWork** และไม่จำเป็นต่อการใช้งานในมหาวิทยาลัย. หัวใจคือ
ตัวคัดกรอง + learning loop. เราจงใจไม่ดันเรื่องนี้เป็นพระเอก.

### Q14. "ทำไมต้อง Rust/WASM ใช้ Python/JS ก็ได้?"
Rust → WASM ให้ 3 อย่างพร้อมกัน: **เร็ว** (ไมโครวินาที), **รันในเบราว์เซอร์**
(ข้อมูลไม่ออกเครื่อง = PDPA), และ **deterministic** (proof เดิมทุกครั้ง). algorithm
เดียวกันรันได้ทั้ง native (server) + WASM (browser) bit-for-bit = พิสูจน์ reproducibility.

### Q15. "ใช้ Kiro ตรงไหนบ้าง (เกณฑ์ 15 คะแนน)?"
spec-driven เต็มรูป: 3 specs (learning-loop, distributable-kernel, voice) แต่ละอัน
requirements→design→tasks. steering files (product/tech/structure) คุมทุก session.
hooks ใน `.kiro/hooks/`. และใช้ Kiro + Amazon Bedrock ช่วยเขียน/ตรวจตลอด —
`.kiro/` อยู่ในรีโป public ให้ตรวจได้.

### Q16. "ถ้าคู่มือผิด คำตอบก็ผิดสิ?"
ใช่ — นั่นคือเหตุผลที่ (1) ไม่ auto-publish (คนอนุมัติทุกคู่มือ), (2) มี 👎 ให้ผู้ใช้
ติ → ลด confidence ของหัวข้อนั้นอัตโนมัติ, (3) abstain เมื่อไม่มั่นใจ. คู่มือผิดแก้ง่าย
(แก้ไฟล์) ต่างจาก AI มั่วที่แก้ไม่ได้ว่ามันจะมั่วเมื่อไหร่.
